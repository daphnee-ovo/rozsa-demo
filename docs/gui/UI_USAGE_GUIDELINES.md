# Rózsa GUI 使用规范

本文定义 Rózsa 桌面 GUI 的产品界面使用规范，适用于 Tauri 桌面端原型、后续工程实现和评审走查。目标不是做一套装饰性的 UI kit，而是保证 Rózsa 的界面始终像一个安静、可靠、权限可控的 coding agent 工作台。

## 1. 设计目标

### 受众

- 日常使用 coding agent 的工程师、维护者和技术团队。
- 需要在桌面端长期停留、审阅工具调用、批准权限、查看代码与 diff 的用户。
- 产品评审者和实现团队，需要从原型直接理解组件职责、状态和交互边界。

### 业务目标

- 让用户清楚知道 agent 正在做什么、用到了哪些工具、是否需要权限确认。
- 保留足够的信息密度，让会话、代码、工具调用和状态可快速扫读。
- 通过温和但明确的视觉反馈表达控制权：用户可以展开、复制、批准、拒绝、切换会话和配置策略。

### 品牌气质

Rózsa 的界面气质是：冷静、精确、递归、专注、安静但有能力。它应像一位资深工程搭档，而不是营销页、IDE 弹窗或终端皮肤。

## 2. 审美标准

### 什么是好看的 Rózsa UI

- **安静的结构感**：用 1px 发丝线、轻背景和清晰分区建立层级，而不是靠厚重卡片和阴影。
- **代码是主角**：聊天、工具调用、代码块、diff 和终端输出应是页面核心，不让装饰元素抢注意力。
- **权限可见但不紧张**：权限模式、风险等级和操作按钮要清楚，但语气和样式不制造警报感。
- **展开意图可发现**：可展开的 tool call、thinking、设置分区通过整体透明度、轻 hover、chevron 和状态点暗示，而不是额外说明文字。
- **状态真实**：运行中、成功、失败、等待审批、限额接近上限等状态必须具体可见。
- **玫红只做信号**：品牌色用于焦点、激活、主操作、进度和少量 hover，不做大面积背景。

### 不能出现的 AI 味 / 模板感

- 不使用紫色、蓝紫色、大面积渐变或发光背景。
- 不使用泛泛的 emoji 功能图标。
- 不使用左侧彩色竖线卡片作为通用模块样式。
- 不把工具调用做成很重的卡片；它应更接近嵌入对话流的命令行记录。
- 不虚构夸张指标，例如“10x faster”“99.9% uptime”。
- 不出现“功能一 / 功能二 / Lorem ipsum”式占位内容。
- 不把设计过程控件、视口选择器、主题旋钮放进真实产品 UI。
- 不使用彩虹式语法高亮；代码阅读应克制、低饱和。

## 3. 视觉系统

### 色彩

只能使用 Rózsa 注册色板及其 token 派生层级。工程实现中应优先引用 token，不在组件里散落新颜色。

| 角色 | 色值 | 用途 |
| --- | --- | --- |
| Background | `#faf8f7` | 应用画布、外层窗口底色 |
| Surface | `#f5f2f0` | 侧栏、浮层、轻面板 |
| Foreground | `#2c2424` | 正文、标题、主要代码文本 |
| Muted | `#8a7a78` | 次级文字、时间、路径、说明 |
| Border | `#e0d6d4` | 分隔线、面板边界、输入框边框 |
| Rose Red | `#c0737a` | 主操作、焦点、激活、关键状态 |
| Rose Red Dark | `#a85e65` | hover、按下态、次级强调 |

使用原则：

- 页面底色保持温暖白，不要变成灰蓝或黑色终端。
- `Rose Red` 每个视图最多承担 1-2 个焦点：例如主按钮和当前上下文进度。
- 状态色如果必须扩展，应低饱和并贴近现有语义，不要引入高纯度绿色、红色、黄色。
- 设置面板选中态优先使用中性色，不使用大面积粉色底。

### 字体

- UI 与正文：Inter 优先，回退到 `-apple-system, BlinkMacSystemFont, Segoe UI, Noto Sans, Helvetica, Arial, sans-serif`。
- 代码与路径：JetBrains Mono 优先，回退到 `ui-monospace, SFMono-Regular, SF Mono, Menlo, Consolas, Liberation Mono, monospace`。
- 基础字号建议为 13-15px；主聊天正文不低于 13px，设置和元信息不低于 11px。
- 数字、限额、耗时、token、行号使用等宽数字，便于对齐扫读。

### 间距与形状

- 使用 4px 基础网格：4 / 8 / 12 / 16 / 20 / 24 / 32 / 48 / 64。
- 常规控件圆角 8px；弹窗和较大容器 12px；小标签和状态 pill 可使用更小或全圆。
- 列表行默认水平 16px、垂直 12px；不要压成 GitHub 式高密度。
- 边框默认 1px；深度优先靠分隔线和轻背景，不靠大阴影。

### 动效

- 动效只用于状态确认、展开收起、流式输出和焦点反馈。
- 常规 hover / active 反馈控制在 80-180ms。
- thinking 运行中可使用轻微闪烁；不要做跳动、弹性或大幅度位移动画。
- 尊重 `prefers-reduced-motion`：关闭非必要动画，保留状态变化。

## 4. 布局规范

### 应用框架

桌面端采用 2:8 信息结构：

- 左侧 2 份：会话列表、状态/限额/工具计数、设置入口。
- 右侧 8 份：当前会话、权限模式、聊天流、工具调用、代码与 diff、输入框。

顶栏只承担窗口感和品牌识别：

- 标题栏层级必须弱，文字小、颜色淡、无强品牌占位。
- 不在顶栏堆导航、CTA 或复杂状态。
- macOS 交通灯只做窗口语义，不参与品牌表达。

### 左侧栏

左侧栏用于导航和状态，不用于承载主要内容。

必须包含：

- 会话列表：会话名、状态点、最近时间。
- 状态区域：分支、diff 摘要、小时限额、本周限额、工具调用计数。
- 设置入口：位于底部，作为稳定锚点。

使用规则：

- 会话名最多一行，溢出省略。
- 状态点必须有语义：运行中、待查看、等待审批等。
- 限额进度条显示百分比与标签；接近上限时使用低饱和警示，不使用高亮警报色。
- 工具计数 chip 只显示真实工具名和数量，例如 Bash、Read、Edit、Write。

### 主区域

主区域的阅读顺序应固定：

1. 当前会话标题与权限模式。
2. 聊天消息流。
3. thinking / tool call / code / diff / summary。
4. 输入框与上下文状态。

主区不要加入营销文案、功能介绍卡或设计说明卡。用户打开应用后应直接进入工作状态。

## 5. 核心组件规范

### 会话项

会话项用于快速切换上下文。

- 激活态用中性背景和轻边界表达，不要用大面积玫红。
- 状态点必须靠近会话标题，避免独立漂浮。
- hover 只提升可读性，不改变布局尺寸。
- 新建会话按钮使用简洁符号或图标，不写长文案。

### 消息

消息由 avatar、role、content 三部分组成。

- 用户与 Rózsa 的消息结构保持一致，但不要使用对称聊天气泡。
- role 标签应轻，避免抢占正文。
- avatar 使用简单字母或品牌标记，不使用表情。
- 内容支持 Markdown，但呈现应融入产品排版。

### Markdown 内容

必须支持：

- 标题 `# / ## / ###`
- 有序列表、无序列表
- 引用
- 链接
- 粗体、斜体
- 行内代码
- 代码块

呈现规则：

- 标题在聊天内应紧凑，不能像文档页面标题一样巨大。
- 引用使用 2px 左边线和 muted 文本，不使用彩色警告样式。
- 链接使用玫红暗色和细下划线，hover 才增强。
- 行内代码使用浅背景、细边框、小圆角。
- 代码块应有语言标签和复制按钮；复制按钮默认弱显示，hover / focus 时显现。
- Markdown 输入框 placeholder / hint 必须明确提示支持 Markdown。

### 代码块与代码视图

代码块分两类：

- Markdown 代码块：用户或 agent 消息里的短代码示例。
- 工具调用代码视图：Read / Write / Edit / Diff 等工具结果中的代码或变更。

共同规则：

- 代码块背景应接近 surface，不用黑底终端作为默认。
- 字号 11.5-12px，行高 1.5-1.6。
- 支持横向滚动，不挤压代码。
- 复制按钮必须可键盘聚焦，并有复制成功状态。
- 语法高亮只能低饱和、少色相；不要使用大块彩色 token。

工具调用代码视图额外规则：

- 行号弱化，不能和代码正文竞争。
- hover 只提供轻行背景。
- 关键字、类型、字符串、注释可以轻度区分，但不要出现鲜艳的 `.kw/.str/.cmt` 彩色贴片感。
- diff 中新增/删除行可以有语义色，但保持低饱和，避免整行强底色。

### Thinking 块

thinking 是可发现但不打扰的过程信息。

- 块始终可见，但默认折叠。
- header 包含图标、状态文案、耗时、chevron。
- 运行中显示轻闪烁和流式输出；完成后显示耗时。
- 点击 header 切换当前块展开；`Ctrl+T` 可切换全部 thinking 展开状态。
- 内容文字使用 muted 或偏淡 foreground，不使用强正文层级。

### Tool call

tool call 是 Rózsa GUI 的核心组件，应像对话中的轻量命令行记录。

结构：

- 左侧：工具图标与工具名。
- 右侧 header：状态点、参数摘要、耗时、chevron。
- 展开体：输出、代码、diff、步骤、错误或摘要。

折叠态：

- 不显示左侧竖线。
- 整体 opacity 稍低，用颜色和透明度提示可展开。
- hover 时工具名、图标、参数和 chevron 变为玫红，背景只轻微变化。

展开态：

- 显示左侧竖线，竖线从图标下方开始，不穿过图标。
- 图标与工具名垂直居中对齐。
- 输出体缩进与轨道对齐，避免像独立卡片漂浮。
- 成功、运行中、错误状态点必须明确。

状态规则：

- `running`：状态点可轻微 pulse，显示正在执行。
- `success`：状态点稳定，必要时显示耗时。
- `error`：显示错误摘要和可恢复建议，不只显示红色。
- `approval`：需要权限时触发权限面板，而不是直接执行。

### 文件变更摘要

会话结束或阶段完成时显示简短摘要容器。

- 展示文件数、文件路径、增删行、总耗时。
- 使用 `+ / ~ / -` 等简短符号标识新建、修改、删除。
- 摘要不应盖过最终回复正文，只做操作结果的结构化补充。
- GUI 必须按当前 turn 展示 `write` / `edit` 返回的 changed files，并展示最近一次 Bash 验证的命令、成功状态、exit code、超时、截断与耗时。

### 输入框

输入区是高频操作面板，必须稳定且可发现。

必须包含：

- 多行 textarea。
- Markdown 支持提示。
- 文件、代码、斜杠命令入口。
- 上下文用量展示。
- 模型选择入口。
- 发送按钮。

交互规则：

- 默认 `Enter` 发送，`Shift+Enter` 换行。
- 默认 `Ctrl+T` 切换 thinking 显示。
- 上述可配置操作以 Keyboard shortcuts pane 中的当前绑定为准。
- 输入框自动增长，但不能挤压到消息流不可用。
- 发送按钮只在可发送状态突出；禁用态使用 muted。
- 权限面板出现时，应停留在输入框上方，保持与当前动作的空间关联。

### 权限面板

权限面板用于确认敏感或需要用户授权的动作。

必须展示：

- 权限标题。
- 风险类型或命令类型。
- 工具名称。
- 命令预览。
- 清晰说明。
- 对复合 Shell 命令，展示尚未信任的命令段及其可选信任范围。
- 操作选项：允许执行、信任本次会话、拒绝执行、拒绝并要求替换方案。

规则：

- 选项保留键盘提示，例如 `Y / T / N / A`。
- `允许执行` 只放行当前调用，不能创建或扩大 session trust。
- `本次会话信任` 使用用户在下拉框中选择的范围；已受信任的命令段不重复出现。单段命令从精确命令逐层提供更宽的前缀范围，例如 `dow status set *`、`dow status *`、`dow *`。
- Trust 只写入 `ROZSA_PROJECT_CONFIG_DIR/settings.json`（默认 `<project>/.rozsa/settings.json`）的 `permission.allow`，因此同一项目的后续会话复用授权；全局 `ROZSA_CONFIG_DIR/settings.json`（默认 `~/.rozsa/settings.json`）的 permission 规则只能手动编辑。
- 匹配顺序固定为 `deny > ask > allow`。同一调用同时命中 deny 和 allow 时必须拒绝。
- 同时排队的请求在正式展示前重评估；前一项新增 Trust 后，后续已经被覆盖的请求直接执行，不重复弹窗。
- 风险标签要具体，例如 Shell 命令、文件写入、网络访问。
- 文案要说明实际影响，不使用恐吓式警告。
- on-request、auto-approve、free-permission 三种模式必须在设置中可见。

### 设置面板

设置面板采用轻量、低对比、融入表单行的风格。

结构：

- 左侧或顶部 tabs：通用、模型、权限、工具。
- 内容区按 group 分组。
- 下拉框、输入框、开关和列表保持一致高度和间距。

规则：

- 选中态使用中性色或极轻玫红，不使用大面积粉底。
- 下拉框弱边框、低对比背景，hover 轻微变化。
- 权限策略配置应包含三种模式说明。
- 周小时限额必须显示进度、当前值和阈值。

## 6. 状态与反馈

### 必备状态

- 空会话：给出可执行的任务示例，不做营销欢迎页。
- 输入中：自动扩展、保留快捷键提示。
- Thinking 中：轻闪烁、流式文字、可展开。
- 工具运行中：状态点 pulse、参数可见。
- 工具成功：状态点稳定、耗时可见。
- 工具失败：显示失败原因、位置和下一步建议。
- 等待审批：权限面板可见，主输入不中断。
- 复制成功：图标或颜色短暂变化。
- 限额警告：进度条低饱和提示，文案清楚。

### 反馈原则

- 所有点击反馈都应小而明确。
- 不依赖颜色作为唯一状态表达，必须配合文案、图标或位置。
- 状态变化不能造成布局大幅跳动。
- 可展开元素必须有 hover、focus 和 chevron / 透明度提示。

## 7. 内容与语气

### 文案语气

Rózsa 的语气应冷静、精确、专业但不冷淡。

推荐用词：

- agent
- tool call
- permission
- session
- context
- recursion
- workspace
- terminal

避免用词：

- 夸张营销词，例如“革命性”“极致”“无敌”
- 拟人化表达，例如“我相信”“我感到”
- 过度口语化 slang
- emoji 作为产品文案或状态符号

### 示例内容

示例必须展示真实能力：

- Markdown 支持应在首屏消息中可见。
- 权限模式和风险确认应有真实命令示例。
- 工具调用应覆盖 Read、Write、Edit、Bash 等主要路径。
- 新增功能后，同步更新示例，让评审者一眼看到变化。

## 8. 可访问性与键盘

必须满足：

- 图标按钮提供 `aria-label` 或可见文本。
- dialog 使用 `role="dialog"`、`aria-modal="true"` 和可理解的 label。
- 所有按钮、链接、输入框、可展开项支持键盘焦点。
- `focus-visible` 使用玫红或等效焦点环，但不遮挡文字。
- 触控目标不小于 44px；桌面密集按钮视觉可小，但可点击区域要足够。
- 文本对比必须满足长期阅读，不使用低对比浅灰正文。
- 错误和警告不能只靠颜色表达。

Keyboard shortcuts pane 展示当前实际绑定；以下是默认绑定和固定的上下文控制：

| 操作 | 快捷键 |
| --- | --- |
| 发送消息 | `Enter` |
| 换行 | `Shift+Enter` |
| 切换 thinking | `Ctrl+T` |
| 关闭弹窗 | `Esc` |
| 权限允许 | `Y` |
| 本会话信任 | `T` |
| 权限拒绝 | `N` |
| 打开拒绝提示 | `H` |

可自定义动作包括发送、换行、聚焦输入框、新会话、模型选择、Settings 和
thinking 展开。修改写入全局配置根目录的 `key_bindings.json`（默认
`~/.rozsa/key_bindings.json`）。权限、问题、自动补全和双击 Escape 等依赖
当前交互状态的控制在页面中只读展示。

Settings navigation 的固定顺序是 Skills、Tools、Extensions、General、Appearance、
Keyboard shortcuts。Skills 和 Tools 都提供 Global/Project 子页；每项可设为继承、
启用或禁用，分别写入对应配置根的 `settings.json`。项目项按名称覆盖全局项。
这两类能力只在新 session 创建时重新装载；已有 session 使用 `/reload` 应用变更。
Tools 列表必须来自实际注册的 core tool 元数据，不能由前端维护第二份静态清单。
Extensions 是明确的预留页面，不得显示尚未实现的开关。

## 9. 实现约定

权限配置文件格式：

```json
{
  "permission": {
    "deny": ["Bash(git push *)", "Edit(./.env)"],
    "ask": ["Bash(npm publish *)"],
    "allow": ["Bash(cargo test *)", "Edit(./src/)"]
  }
}
```

`*` 表示命令或路径前缀；未带 `*` 的 Bash 规则精确匹配。`deny`、`ask`、`allow` 分别适用于 Bash 与文件工具，顺序不可调整。

- 主要区域和可调元素应保留稳定的 `data-od-id`，便于检查和后续精修。
- 组件样式优先复用现有 token，不在组件内新增散乱色值。
- 单文件原型可以保留内联 CSS / JS；工程化时可拆分为 `styles/` 与 `components/`，但命名和状态语义不变。
- 复杂交互必须有真实行为：展开、复制、权限选择、设置 tab、发送消息、自动增长、autocomplete。
- 不把说明文档、设计规范或调试控件塞进产品界面。
- 新增 UI 模块时，必须同步考虑空态、加载态、成功态、错误态、键盘态和移动/窄屏降级。

## 10. 评审清单

交付前逐项检查：

- [ ] 顶栏是否足够弱，没有抢主内容层级？
- [ ] 左侧栏是否只承担会话、状态和设置，不承载主要任务？
- [ ] 主区域是否以当前会话和对话流为中心？
- [ ] tool call 折叠态是否没有竖线，展开态竖线是否从图标下方开始？
- [ ] tool call 是否通过透明度、颜色和 chevron 提示可展开？
- [ ] 工具图标是否足够清楚，并与工具名平齐？
- [ ] Markdown 标题、列表、引用、链接、行内代码、代码块是否都能正确显示？
- [ ] 代码块是否克制、可复制、可横向滚动？
- [ ] 权限面板是否说明风险、工具、命令和四种操作？
- [ ] 设置面板控件是否低对比、不突兀？
- [ ] 输入框是否提示支持 Markdown？
- [ ] 小时限额、本周限额、工具计数和状态点是否可见？
- [ ] 是否没有紫色渐变、emoji、重卡片、假指标和模板化占位？
- [ ] 是否所有交互都有 hover / focus / active 状态？
- [ ] 是否所有图标按钮都有可访问名称？

## 11. 后续扩展边界

优先扩展：

- 多会话搜索与分组。
- 工具调用过滤和错误定位。
- 权限策略模板。
- 代码预览与 diff 独立面板。
- 周限额明细和重置时间。

谨慎扩展：

- 暗色模式：必须保持 Rózsa 的温暖气质，不变成黑色终端。
- 移动端：应重排信息架构，不能简单压缩桌面三栏。
- 高级主题：不应暴露为产品内设计旋钮，除非它是真实用户设置。
